# 当前 App 耗电分析

> TUN 链路的专项电量分析见 [TUN_POWER_ANALYSIS_ZH_HANS.md](TUN_POWER_ANALYSIS_ZH_HANS.md)。

## 结论范围

这是基于当前源码的静态分析，不等同于某一台设备上的实测电量。真实耗电还会受 SoC、网络制式、代理流量、屏幕亮度和系统后台策略影响。

## 场景矩阵

| 场景 | 当前主要工作 | 耗电风险 | 结论 |
| --- | --- | --- | --- |
| App 空闲、代理未启动 | UI 状态流、事件接收器、按需预览刷新；统计页时钟仅在有订阅者时每分钟更新；WorkManager 存储清理（约 15 分钟一次、机会式执行） | 低 | 没有持续网络轮询，后台定时任务由系统批处理 |
| App 前台、Tun/HTTP 运行 | 客户端流量查询（亮屏且前台时每 2 秒）、运行状态刷新（每 4 秒，代理页可见时每 2 秒）、显示模式同步（每 5 秒）、连接快照（统计页可见时每 1 秒，其余前台时间每 5 秒）；流量统计前台 5 秒采样、30 秒批量落盘；服务通知每 2 秒刷新（仅开启流量通知时，且仅在文本变化时真正重建）；日志流仅在有人取日志时打开 | 中 | 高频工作集中在用户正在查看 App 时；统计落盘已做批量合并，运行负载/连接/模式轮询均按前台+亮屏门控，连接快照另按订阅门控 |
| App 退到后台、Tun/HTTP 运行 | native 核心持续转发；服务通知在亮屏且开启流量通知时每 2 秒刷新；客户端流量、显示模式、连接快照三类轮询全部挂起 | 中到高 | 转发耗电取决于实际流量；通知刷新仍是唯一的固定后台工作 |
| App 退到后台、屏幕熄灭、Tun/HTTP 运行 | native 核心持续转发；通知测速暂停；客户端轮询全部挂起；流量统计降为 30 秒采样；日志流在无人取用 20 秒后自停 | 中 | 已避免无用户可见收益的高频 UI 轮询；核心网络耗电无法在不停止代理的情况下消除 |
| RootTun 运行 | RootTun 状态 IPC；亮屏约 4 秒、熄屏约 30 秒轮询（点亮屏幕立即补一次），熄屏时跳过流量内容更新，内容未变化时跳过通知重建 | 中 | 状态通知轮询有固定 IPC/唤醒成本，熄屏档已按用户不可见放宽 |
| 通知栏快捷开关可见 | 磁贴状态每秒检查，仅在状态/副标题变化时推送更新（仅系统在下拉通知栏、且磁贴被监听时运行，收起后自动停止） | 低 | 只在用户查看通知栏期间短暂运行 |
| 代理组测速 | 每个目标发起健康检查；随后多次延迟刷新（由 native 核心 url-test 决定） | 高（短时） | 只应由用户主动触发；批量测速会产生多次网络握手和无线电活跃 |
| 配置下载/刷新 | 网络请求、配置解析、运行时重载 | 高（短时） | 受网络质量和配置大小影响，不是常驻耗电源 |
| 日志记录 | native 日志订阅、跨 JNI/进程传递、落盘（Root 模式约每 2 秒轮询一次）；无消费者时不打开日志流 | 中 | 高日志量时会产生 CPU、序列化和 I/O；建议仅在诊断期间开启 |

## 关键周期与降耗措施

- 流量统计：前台/亮屏 5 秒采样、后台或熄屏 30 秒采样，差异先在内存累计，每 30 秒批量写入一次 MMKV（运行时停止时也会落盘），比逐样本写入约降低 6 倍 CPU/闪存开销；差值按真实采样窗口比例落桶，降频只影响「多小时分布」的粒度，不影响每日总量
- 客户端状态轮询：亮屏 + 前台 + 运行中时每 2 秒查流量；任一条件不满足即降为 60 秒空转（不触发 JNI/Binder 查询），返回前台或亮屏时立即恢复高频节奏
- 显示模式同步（首页/代理页共用控制器）：运行中且亮屏 + 前台时每 5 秒查一次核心模式（后台或熄屏时完全不查询）。App 自身发起的动作（启停、模式切换、回到前台）仍会立即刷新，5 秒只是兜底；代价：完全绕过 App 的模式变化（例如配置重载导致）最迟 5 秒后写回显示模式
- 连接快照（“最近请求”数据源）：唯一的消费方是流量统计页。该页订阅着时每 1 秒采样一次（用于捕获短连接），没有订阅者时降到每 5 秒「保温」采样，为下次打开该页保住历史；后台或熄屏时两者都挂起（不唤醒、不查询）。关闭连接由 Go 侧采样器持续捕获，并按「是否已被某次轮询取走」分两档过期：取走过的按 6~8 秒窗口（跟随实测轮询间隔）过期，**未被取走的**（即 App 不可见期间关闭的）保留 30 分钟、上限 500 条。为避免 RootTun 路径的 AIDL JSON 字符串撑爆 binder 事务，单次响应最多回放 200 条（按最旧优先），积压由之后几次轮询排干、不会丢。因此回到前台后的头几次轮询会把离去期间的历史补齐，并带上核心记录的**真实关闭时间**
- 服务流量通知：仅亮屏且开启“流量通知”时每 2 秒刷新；熄屏或关闭后循环自停，不产生后台唤醒；标题/正文与上次一致时跳过通知构建与 `notify()`
- RootTun 通知：亮屏 4 秒 / 熄屏 30 秒轮询，收到亮屏广播立刻补一次（避免解锁瞬间看到过期流量行）；熄屏时跳过流量内容更新，标题/正文未变化时跳过通知重建
- 配置/选择缓存：`ProfileStore` 以 MMKV 原始串为缓存键，内容未变时不重复反序列化；活跃配置查询改为单次查表
- 快捷磁贴：状态轮询每秒检查一次，但仅在状态或副标题变化时才 `updateTile()`；MMKV 读取放在 IO 线程
- 存储清理：WorkManager 每 15 分钟周期任务（`NOT_REQUIRED` 网络、系统机会式批处理），冷启动时顺带清理一次
- 统计页时钟、最近请求、今日汇总等均为 `WhileSubscribed` 订阅流：无 UI 订阅者时自动停止（约 5 秒延迟停）
- 日志页浏览：仅在日志页可见时自动刷新，间隔 1 秒（重新列出日志目录）；实时缓冲改为按「写入代次」判定，没有新日志行时直接复用上次解析结果，不再重复解析最多 2000 行
- 运行载荷（全部代理组 + providers + 配置）：服务侧按「快照实例 + 已持久化选择」做记忆化，JSON 编码同样复用；快照 TTL 到期后重建的载荷若与上一次内容相等，则直接复用上一次的实例（连同已编码字符串），所以无人操作时既不会重算也不会重编码 O(全部节点)；载荷里已不含每次必变的流量字段。本地归属路径（`ClashManager`，本地 Tun/HTTP 模式）对「核心载荷实例 + 已生效选择」再加一层呈现结果记忆化：两者都没动时连 `SelectionPresentation.apply` 的 O(全部节点) 校验与整份 copy 也一起省掉（与 root 归属的 `SessionRuntime` 同一套做法）
- root 运行时的载荷另带一个「实例锚点 + 版本」戳：客户端拿到同一戳时直接复用自己的副本，连跨 binder 传输与 JSON 反序列化都省掉（仅 RootTun 模式；锚点取自单调时钟，root 进程重启后必然不相等）
- 本地运行载荷的内容戳：本地 Tun/HTTP 模式下客户端与核心同进程，载荷不跨 binder，但每次刷新仍要全量 marshal、跨 JNI 复制成 UTF-16 字符串并全量反序列化。Go 侧新增 `queryRuntimeSnapshotStamp()`——对载荷序列化的每一个字段做零分配 FNV-1a 内容哈希——命中时客户端直接复用已解码副本（30 秒兜底 TTL），代理页 2 秒 / 其它前台 4 秒的刷新在载荷未变时只剩一次 64 位调用
- 最近请求列表：统计页可见时随连接快照每秒重建。原先对「全部活跃连接 + 最多 300 条已关闭连接」都在排序比较器里解析一次起始时间（O(n log n) 次 ISO-8601 解析）并构建完整行对象后才截断到 100 行；现在每条连接只解析一次、无搜索词时先截断到 100 行再建行，源应用解析走 `PackageManager` 正向缓存（原先每条连接每次重建都要查询一次），行内链解析由 3 次 map/filter 合并为 1 次
- 日志流按需打开：没有日志消费者时不订阅核心日志（无 marshal/JNI/decode，也不向 logcat 转发 info/debug 行），最后一个消费者离开 20 秒后自动停止；ERROR/WARNING 仍保留在 logcat 便于快速排障

## 本轮修复（日志 / 载荷 / 采样 / 重组）

| 项 | 问题 | 改动 |
| --- | --- | --- |
| 日志订阅泄漏 | `subscribeLogcat()` 从不退订，Go 侧订阅 goroutine 与 JNI 全局引用常驻；每条核心日志被 marshal + JNI + decode k 次，并向所有仍打开的 channel 重复 fan-out（日志页/录制文件出现重复行） | 新增 `unsubscribeLogcat()`（Go `lib/native/go/native/log.go`、C++ `main.cpp`、Kotlin `Bridge.nativeUnsubscribeLogcat`），最后一个 channel 关闭时退订；无订阅者时不解析 JSON |
| 载荷往返 | `queryRuntimeDataSnapshot()` 每 tick 全量 marshal + decode（O(全部节点)），且载荷内的 `trafficNow/trafficTotal` 每 tick 变化，使任何缓存都无法命中 | 从载荷中移除流量字段（无人消费），服务侧对「快照 + 选择」与序列化结果分别记忆化 |
| 轮询节奏 | 延迟测试期间 250ms、代理页空闲 2 秒的请求都可能在每次 tick 触发一次完整重算 | 测试期 500ms、空闲 3 秒；真正的重建由 1 秒合并窗（等于载荷 TTL）归并，单次重建成本也因记忆化大幅下降 |
| 统计采样 | 熄屏后仍按 5 秒采样 | 非前台/熄屏时降为 30 秒采样（差值仍按真实窗口比例落桶） |
| RootTun 熄屏轮询 | 熄屏仍 8 秒轮询一次状态 IPC | 熄屏 30 秒 + 亮屏广播提前唤醒，解锁瞬间的通知行不会过期 |
| 首页流量重组 | `trafficNow` 并入 Eagerly 的 `screenState`，每 2 秒重组整个首页 | 流量拆成独立流并在叶子读取（`HomeRoute` 传入延迟取值），只有流量卡片重组 |
| 测速旋转 | 每个节点卡片的旋转动画常开，且按帧重组 | 仅在测速时启动动画，角度改由 `graphicsLayer` 在绘制阶段读取 |
| 半窗模糊 | 弹窗期间窗口常驻 `FLAG_BLUR_BEHIND` | 半径为 0 时不再挂模糊标志（模糊本身仍是设计意图，进出场按 3 档渐变提交窗口事务） |

## 本轮修复（连接快照门控 / 模式同步 / 日志增量 / 载荷内容复用）

| 项 | 问题 | 改动 |
| --- | --- | --- |
| 连接快照订阅门控 | 只要「前台 + 亮屏 + 运行中」就每 1 秒做一次全量连接 JSON 查询（binder + 反序列化 + 历史比对），而唯一消费方是流量统计页 | `ConnectionActivityRepository` 统计自身流的订阅者：有订阅者保持 1 秒，无订阅者降为 5 秒保温并在新订阅者出现时立即唤醒；`ConnectionHistoryManager` 的关闭去重由线性扫描改为 id 集合 |
| 关闭连接保留窗口 | Go 侧固定保留 2 秒，比 5 秒保温档短，会丢掉一部分关闭记录 | `tunnel/conn.go` 保留窗口下限提到 6 秒（覆盖最慢档），并按实测轮询间隔自适应放宽（上限 8 秒），保证「任何一档下每个关闭都被下一次轮询看到」 |
| 后台期间关闭的连接不入历史 | 保留窗口只有 6~8 秒，且轮询在后台/熄屏时挂起，所以 App 不可见期间关闭的连接等回到前台时早已过期，永远进不了「最近请求」 | `tunnel/conn.go` 把「是否已被某次轮询取走」作为过期依据：未被取走的保留 30 分钟（上限仍 500 条），取走后仍按 6~8 秒过期，所以后台不产生任何额外唤醒或轮询；同时载荷新增 `closedAt`，`ConnectionHistoryManager` 优先用核心记录的关闭时间入历史（原先用轮询时刻，批量补记会全部显示成「刚刚关闭」） |
| 显示模式同步兜底频率 | 每 1.5 秒查一次核心模式，而 App 自身动作已全部立即刷新 | 兜底频率放宽到 5 秒（启停/切换/回到前台仍是立即） |
| 日志页重复解析 | 日志页可见时每秒重新列出日志目录并重新解析最多 2000 行实时缓冲，即使一行未增 | 缓冲新增写入选代次（`LogRecordService.liveLogRevision`），代次未变则复用上次解析结果 |
| 载荷内容复用 | 快照 TTL 到期后重新构建的载荷与上一次内容相同，却仍会重新编码整份 JSON、跨 binder 传输并全量反序列化 | `SessionRuntime` 在重建载荷后做内容相等判断，相等则复用上一次实例（连带已编码字符串）；`UiConfiguration` 改为 `data class` 以支持该比较 |
| 载荷体积可观测 | 载荷接近 binder 事务上限时只会以模糊的 IPC 错误暴露 | 编码结果超过 512 KiB 时打印告警；`binderFailureReason` 单独识别 `TransactionTooLargeException` |
| 死常量 | `AppConstants.Timing`（9 个）与 `AppConstants.Limits`（3 个）全无引用 | 删除 |

## 本轮修复（root 载荷戳 / 选择查找批量化 / 行缓存）

| 项 | 问题 | 改动 |
| --- | --- | --- |
| root 载荷跨进程复用 | 即使服务侧已记忆化、载荷内容未变，客户端每次刷新（代理页 2 秒、其它前台 4 秒）仍要把它整份跨 binder 传一遍再全量反序列化，成本随节点数线性放大 | `SessionRuntime` 新增 `runtimeDataStamp()`（实例锚点 + 载荷版本，版本只在载荷真的变化时前移）；AIDL 增加 `queryRuntimeSnapshotStamp()`；客户端 `RootTunPayloadCache` 按戳复用解码结果，未变时只剩一次两 long 的调用；binder 断开/重连即清空缓存 |
| 快照选择查找 | 每次运行快照（约 1 秒一次）为每个代理组各读一次持久化选择（`mmkv.decodeString` + `filter`），N 个组即 2N+1 次读取与 2N 次列表分配 | `SelectionLookup` 按组名一次索引（`ClashManager` 快照/全部组/单组三条路径共用）；等价性由 `SelectionLookupTest` 锁定 |
| 首批选择写入 | 新装/换配置后的首个快照会逐组 `setSelected`，每次都全量 JSON 编码 + 写 MMKV（O(n²) 编码 + N 次写） | 新增 `SelectionDao.setSelectedAll`，快照内收集后一次合并落盘（语义与逐条调用一致） |
| 列表行分块与 key | 代理页/节点网格的行分块与行 key 在 `LazyListScope` 扩展里现算，每次重组都重新 `chunked` 并拼接 O(行数) 个 key 字符串，而负载刷新常见为 1~2 秒一次 | 新增 `rememberLazyRows`：按「列表 + 列数」记忆化行分块与 key，只在真正变化时重算（key 形状不变，重名节点仍安全） |

## 本轮修复（本地载荷戳 / 最近请求管线）

| 项 | 问题 | 改动 |
| --- | --- | --- |
| 本地模式载荷往返 | RootTun 模式已有「载荷戳」，本地 Tun/HTTP 模式（客户端与核心同进程）仍是每次刷新都全量 marshal + 跨 JNI 复制成 UTF-16 字符串 + 全量反序列化，代理页每 2 秒、其它前台每 4 秒各一次，成本 O(全部节点) | Go 侧新增 `queryRuntimeSnapshotStamp()`：对 `queryRuntimeSnapshot` 序列化的每个字段（配置 / providers / 代理组 / 节点）做零分配 FNV-1a 内容哈希；`Clash.queryRuntimeSnapshot()` 先比戳，命中即复用已解码副本，并带 30 秒兜底 TTL（将来给载荷加字段却漏进哈希时，最多晚 30 秒而不是永久不刷新）；「取载荷 → 复查戳」的复查在锁外取值，避免 O(全部节点) 的 native 遍历占着 `runtimeSnapshotLock` 让其它调用者陪跑 |
| 最近请求列表重建 | 统计页可见时每秒重建一次：`sortedByDescending { parseConnectionStartMillis(...) }` 在比较器里解析 ISO-8601（每次比较一次解析，O(n log n) 次），且「全部活跃连接 + 最多 300 条已关闭连接」都先构建完整行对象才截断到 100 行；每个行对象还会查询一次 `PackageManager` 解析源应用、并对 chains 做 3 次 map/filter | `DefaultTrafficStatisticsExplorer` 改为先按起始时间排序（每条连接只解析一次）→ 无搜索词时先截断到 100 行再建行；`AppIdentityResolver.findInstalledPackage` 增加正向缓存；行内链解析合并为一次 |

## 真机验证方法

建议在同一设备、同一网络和同一代理配置下，各记录 30 分钟：无代理空闲、Tun 无流量、Tun 持续下载、亮屏首页、流量通知开关两种状态，以及 RootTun 与本地 Tun 两种模式。

可用 `adb shell dumpsys batterystats --reset`、`adb shell dumpsys batterystats <package>` 和 Battery Historian 对比；同时记录 `adb shell dumpsys cpuinfo`、`adb shell dumpsys netstats`，避免把网络本身的耗电误判为轮询开销。
